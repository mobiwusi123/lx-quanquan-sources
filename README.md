# 圈圈音源 (lx-quanquan-sources)

洛雪音乐（lx-music）自定义音源脚本，从 v3 一路迭代到 v14 的完整留档喵。

## 这是什么

一个跑在洛雪音乐「自定义源」里的 JS 脚本：当播放器要播一首歌时，它负责把「歌名 + 歌手」换成一条**可播放的音频 URL** 交回去喵。

它不下载、不缓存、不转码，只是一层**取链接的中间人**喵。

## 怎么用

1. 打开洛雪音乐的「设置 → 自定义源 → 导入」喵。
2. 选仓库根目录的 [`圈圈音源.js`](./圈圈音源.js)（v14 最终版）喵。
3. 源列表里会出现「圈圈音源」，启用它即可喵。

脚本向播放器声明了 5 个音乐平台，界面里可以逐个勾选喵：

| 平台 ID | 名称 | 声明音质 |
| --- | --- | --- |
| `kw` | 酷我音乐 | 128k / 320k / flac |
| `mg` | 咪咕音乐 | 128k / 320k |
| `tx` | QQ音乐 | 128k / 320k / flac |
| `wy` | 网易云 | 128k / 320k / flac |
| `kg` | 酷狗 | 128k / 320k / flac |

> **注意**：声明的是 5 个平台，但 v14 实际的解析分支只有 `Kuwo` 与 `MiGu_Music` 两个端点，`tx / wy / kg` 没有对应的取链逻辑，勾了也不会生效喵。
>
> 这个收缩发生在 **v10**，不是 v13：v9 时还是五源直连（各自有 `kwGet / txGet / mgGet / kgGet / wyGet` 五个函数，用 `MAP` 分发），v10 起 `sources` 只剩 `kw`，v12 同样只有 `kw`，v13 才补回 `mg`。v13 到 v14 之间 `sources` 块又被写回 5 个，但解析逻辑仍只走两路，属于声明与实际能力不一致喵。
>
> oiapi 现状实测（2026-11-04）：`Kuwo`、`MiGu_Music` 均返回 200 可用；`QQ_Music` 返回 403「接口暂时无法访问」，`Netease_Music` / `Kugou` / `QQ` / `WY` / `KG` / `Music` 全部 302 重定向喵。

## 原理：一条链接是怎么拿到的

```
播放器要歌
   ↓
payload.info.musicInfo  ← 从这里取 name / singer / source / type
   ↓
拼「歌名 + 歌手」→ 请求 oiapi 接口
   ↓
pickUrl 拆出真实 URL（JS 对象 → 正则 → 裸链接 三级兜底）
   ↓
按音质改写 bitrate 参数
   ↓
交回播放器
```

三个设计点值得记一笔喵：

- **读对字段**：歌曲信息藏在 `payload.info.musicInfo` 里，不在顶层 `info`。v14 之前一直读错位置，才会「明明有歌却报 no name」喵。
- **四级降级链**：`[源平台+歌名歌手] → [另一平台+歌名歌手] → [源平台+纯歌名] → [另一平台+纯歌名]`，全部失败才 reject `all failed`，用「多打几枪」换成功率喵。
- **超时兜底**：`httpOnce` 自带 12 秒定时器，配合 v7 引入的自适应超时，是为了避开洛雪自己那条 20 秒硬限制——超时不是报错，是换下一个源喵。

## 版本演进

| 版本 | 一句话 |
| --- | --- |
| v3 / v4 | 五平台取播放链接的初版与修补 |
| v5 | 带重试，抗首包慢 |
| v6 | 短超时快速换源，抗服务器慢 |
| v7 | 自适应超时，避开 LX 的 20 秒硬限制 |
| v8 | 酷我直连，绕过慢中转，0.5 秒取链接 |
| v9 | 四源直连，全部 1 秒内 |
| v10 | oiapi 聚合源，酷我直连秒出链接 |
| v11 | 酷我直连秒出 320k |
| v12 | 多接口兜底 |
| v13 | 双平台策略成型：酷我 + 咪咕，任一可用即可 |
| v14 | 修正 musicInfo 解析，**当前最终版** |

看得出来整条路线的重心：**v3–v7 在解决「慢」，v8–v12 在解决「稳」，v13–v14 在解决「对」**喵。
